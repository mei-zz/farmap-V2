# FarMap Commercial Product Audit

审查对象：FarMap V2 当前 `feature/commercial-product` 分支

审查目的：判断当前系统是否已经从 Research Prototype 演进为可对外展示、可持续运营的 Agricultural AI Decision Platform。

审查方式：基于当前前端路由、页面组件、Demo/Real 模式切换、Agent Runtime、Multimodal RAG、Operations 与 Expert Review 的实现进行静态产品审查。当前环境未进行浏览器截图与真实账号逐步操作，因此视觉密度、响应式细节、真实接口延迟和权限边界仍需要在后续 UI 评审中补充验证。

## Executive Verdict

FarMap 已经具备农业 AI SaaS 的产品骨架：有农场工作台、GIS 地块上下文、诊断报告、证据链、Agent 运行过程、人工审批、Operations 任务与专家复核入口。产品叙事也已经从“调用模型得到答案”转向“发现风险—解释依据—生成建议—审批执行—专家反馈”。

当前仍不能视为完整的企业级 Agricultural AI SaaS。主要原因是核心页面同时承载了 Demo 数据、Real 数据和技术调试信息，部分一级导航仍是占位页，审批与任务执行在用户界面上没有形成清晰的状态机，Knowledge & Expert 尚未成为可持续运营的工作区。用户可以看到系统拥有 AI 能力，但还不能始终理解哪些结果已经发生、哪些只是演示、下一步由谁负责以及行动是否真的完成。

**商业成熟度：72/100。**

- 产品定位：16/20。农业、GIS、AI 与专家闭环的定位清楚，但商业承诺仍被 Demo/Real 混用削弱。
- 用户流程：14/20。主路径可以串起来，审批和执行状态的可见性不足。
- UI/UX：15/20。Overview、Diagnosis、Agent 已有产品化结构，信息层级和跨页一致性仍需收敛。
- AI 能力展示：16/20。多模态、证据、Agent 与模型路由均有展示，但技术字段偏多，业务价值的优先级还不够稳定。
- 商业可信度：11/20。专家复核、证据和状态标签是优势；真实数据覆盖、审计、任务结果和空状态的产品表达仍不完整。

作为科研与答辩型系统，当前完成度约为 **88/100**；作为可交付给农业管理团队的商业产品，当前更接近 **Pilot-ready foundation**，还没有达到规模化 SaaS 的稳定标准。

## 1. Product Position

### 当前定位

FarMap 当前最准确的定位是：

> 面向农场管理者和农业专家的多模态农业智能决策平台，通过 GIS、图像、气象、物候、土壤、知识与历史案例，为地块风险提供可解释诊断，并将批准后的建议转化为农事任务。

这个定位已经超过单纯的 Research Prototype，因为系统具备：

- 面向业务对象的 Farm、Field、Diagnosis、Operations、Expert Review 模型。
- 以地块和农情问题为中心的跨页面上下文。
- Multimodal RAG、Evidence Grounding、Agent Tool Calling 和模型路由。
- 写操作需要审批，任务可回链到 Agent Run 与诊断。
- 专家确认结果可以进入历史案例候选，形成 Human-in-the-loop 方向。

### 与企业 AI 产品标准的距离

当前产品仍处在“商业产品外壳 + 可验证的 AI 核心”的阶段。它可以用于答辩、客户演示和试点验证，但还需要解决以下企业购买者关心的问题：

1. 一个风险从发现到关闭的责任人、截止时间和结果证据是否始终可见。
2. 一个诊断是 REAL、DEMO、失败、待复核还是已确认，是否不会被用户误读。
3. 管理者是否可以在不理解 RAG 或 Agent 的情况下完成决策。
4. 专家是否有足够的队列、筛选、批量处理和反馈统计工具。
5. 任务完成后是否能回写“实际结果”，并用于下一轮风险评估。

## 2. User Journey

目标路径：进入系统 → Overview → 选择农场/地块 → Digital Farm → AI Diagnosis → Agent Workspace → Evidence → Recommendation → Human Approval → Operations Task → Expert Feedback。

| 用户步骤 | 当前页面/实现 | 完成度 | 主要问题 | 商业建议 |
|---|---|---:|---|---|
| 进入系统 | Landing、Login、Demo Entry | 部分完成 | 演示入口与正式登录并存，用户不一定理解当前数据是否真实 | 首屏明确环境、数据范围、账号角色和下一步任务 |
| Overview | `/overview` | 基本完成 | 指标、地图、风险、天气和任务集中展示，但多数内容为 Demo 数据，卡片行动不总是可点击 | 将首屏改成“今日需要决策的 3 件事”，每条风险绑定责任、时间和下一动作 |
| 选择农场/地块 | Header Farm Select、AI Context | 基本完成 | 农场选择能更新上下文，但地块选择主要依赖地图或固定 A-12 演示路径 | 提供统一的 Farm → Field 选择器，并在每页显示当前上下文和数据更新时间 |
| Digital Farm | `/farm/map` | 部分完成 | GIS 可展示地块与指标，但地图层、标注、测距等入口缺少完整反馈；正式模式还依赖后端农场数据 | 把地图选择直接连接风险、诊断和任务，提供 Field Intelligence Panel |
| AI Diagnosis | `/diagnosis/a12-demo`、`/diagnosis/new` | 基本完成 | 报告结构清楚，但 Demo 路径固定 A-12；生成报告、编辑、相关操作部分仍是未完成动作 | 明确输入、结论、证据、风险、建议、复核状态和报告导出状态 |
| Agent Workspace | `/analysis/a12-demo`、`/analysis/:runId` | 基本完成 | 运行步骤和工具链很完整，但屏幕仍有大量 Tool Trace、技术字段和演示固定结论 | 默认展示目标、进度、证据、结论、待审批动作；技术追踪放入 Expert Mode |
| Evidence | Diagnosis 的证据 Tab、Agent Evidence Preview | 部分完成 | 有分类、来源和证据卡片，但证据与具体建议、风险等级和冲突处理的关系不够直接 | 每条建议显示依据、来源时间、置信度、冲突和“为什么这样建议” |
| Recommendation | Diagnosis 农事建议、Agent 输出 | 部分完成 | 建议卡片存在，但优先级、责任人、截止时间和执行前置条件没有统一 | 统一为可审批的 Action Card，并在审批前明确影响范围和撤销方式 |
| Human Approval | Agent action approve、Expert Review 提交 | 部分完成 | 审批入口分散在 Agent 与诊断复核中，缺少独立审批队列和状态历史 | 建立统一 Approval Center，区分 AI 建议审批、专家复核和任务执行确认 |
| Operations Task | `/operations/tasks` | 部分完成 | 已能展示审批后的 Agent 任务，但任务详情、执行证据、负责人和完成回写不足；“问专家”是外部 iframe | 增加任务详情、步骤、负责人、截止时间、现场证据、完成/撤销/异常状态 |
| Expert Feedback | `/knowledge/expert-review` | 部分完成 | 有待修改列表和复核状态，但 Knowledge Library、Cases 等仍是占位页，反馈到模型/案例的结果不可见 | 建立专家队列、案例质量、反馈采纳和历史案例入库状态 |

### 用户理解成本

- 页面命名在中文与英文之间切换，例如“智能分析 / Agent 工作空间”“Knowledge & Experts”，需要统一任务语言。
- 同一份数据可能以 Overview 卡片、Diagnosis 报告、Agent 运行记录和 Operations 任务四种形式出现，但对象 ID 和状态没有始终显式关联。
- “Evidence”“Runtime Mode”“Milvus”“Historical Retriever”等技术标签对专家有价值，对农场管理者会增加阅读负担。
- Demo Mode 标签存在，但页面中的时间、指标、历史案例和设备状态仍足够逼真，缺少更强的演示水印和数据说明。

## 3. Information Architecture

当前一级导航：Overview、Smart Farm、AI Diagnosis、Agent、Operations、Knowledge & Experts、Settings。

结构方向正确，符合农业 AI 平台的核心对象，但二级信息架构还没有完全支撑商业运营：

- Smart Farm 下有地图、地块、设备与监控，但地块管理和设备页面在演示/正式模式之间不一致。
- AI Diagnosis 下有新建、详情和历史；历史在正式角色可访问，演示模式会被禁止，缺少统一诊断记录入口。
- Agent 页面有工作空间和运行详情，但缺少 Runs 列表、审批队列和失败重试中心。
- Operations 下有任务、推荐，但推荐页是占位页，任务缺少详情页和执行结果页。
- Knowledge & Experts 下有知识库、专家复核、案例库，但知识库和案例库仍为占位页，无法形成运营闭环。
- Settings 只对管理员开放，模型和系统配置是占位页；这对试点足够，但对企业运维不够。

一级菜单数量合理，用户理解成本主要来自页面之间的状态连接不足，而不是导航数量过多。

## 4. Page Audit

### 4.1 Overview

**判断：已经像农业智能驾驶舱，但仍有 Demo Dashboard 的痕迹。**

优势：

- 顶部健康度、地块数、面积、设备在线等指标能快速建立农场全局感知。
- 地图、AI Insight、天气、监控、农事任务、最近诊断和动态构成了完整的业务入口。
- AI Insight 使用风险、证据数、置信度和数据来源，具备“先发现问题再采取行动”的商业叙事。
- Copilot 和 Agent 入口都在首屏，降低了从观察到提问的距离。

问题：

- “农场健康度 86/100”“3 个问题”“4 项待执行”等关键数字与固定 Demo 数据绑定，真实模式下的来源和更新时间不够显眼。
- 风险卡片可以跳转，但缺少严重程度、影响面积、负责人、截止时间和风险趋势。
- 地图上的“卫星影像、NDVI、地块边界、图层、标注、测距”部分更像工具栏，尚未明确每个图层如何改变决策。
- 天气、监控和任务卡的“查看详情/查看全部”有些只是视觉入口，跨页动作不完整。

商业建议：首屏从“数据总览”收敛到“今日决策队列”，只突出高影响风险、需要审批的建议和逾期任务；其余指标放入次级区域。

### 4.2 Digital Farm

**判断：GIS 是空间入口，但还没有完全成为 AI 决策入口。**

优势：

- 地图支持作物、地块位置、信息指标和范围滑块，能承载空间分析。
- Farm 与 Field 上下文会写入 AI Context，具备跨页面传递基础。
- A-12 地块在 Overview、Diagnosis、Agent 之间有连续叙事。

问题：

- 地图选择后，用户下一步要点哪里才能看到风险、证据或诊断不够明确。
- 当前地图页重点是图层和指标控制，缺少选中地块的风险摘要、最近诊断、待办任务、数据质量和“启动分析”面板。
- 正式模式 fetch 失败时缺少面向用户的空状态、重试和数据权限解释。
- 地图颜色、风险等级和业务动作之间缺少统一图例与可访问文本。

商业建议：增加 Field Intelligence Panel，把选中地块固定为“健康状态、风险、证据、最近任务、启动诊断”五个业务区块；地图只负责空间定位，面板负责决策。

### 4.3 AI Diagnosis

**判断：最接近专业 AI 报告，但需要更强的业务视图。**

优势：

- 报告具有结论、风险等级、置信度、替代可能性、核心证据、证据关系、农事建议和专家复核。
- Evidence 卡片显示类别、来源、时间和描述，能支撑 Evidence → Reasoning → Recommendation。
- REAL RAG 与技术详情可显示模型路由、嵌入模型、Milvus、检索和生成延迟。
- 提交专家复核、生成任务、加入案例库等动作已经表达了后续闭环。

问题：

- “生成报告”“编辑”“生成完整诊断报告”“创建巡检任务”“加入历史案例库”等按钮的完成反馈和状态不统一，容易让用户以为动作已完成。
- 业务结论与技术详情混在同一页面的可见层，管理者需要穿过模型和 Milvus 信息才能抓住建议。
- 置信度、风险等级和替代可能性缺少解释，用户无法判断该如何决策。
- 历史案例为空时，报告仍可能出现固定 Demo 案例叙事，REAL/DEMO 边界必须更明确。

商业建议：默认使用 Business View：结论、影响范围、建议、风险、依据、待审批动作；将 Technical View 折叠为 Expert Mode，并给出“证据不足/冲突/需复查”的明确结论。

### 4.4 Agent Workspace

**判断：功能上是 Agent 产品，视觉和信息上仍接近 Developer Debug Console。**

优势：

- 有任务目标、上下文、数据源、步骤、运行状态、工具调用、证据预览、结论、动作审批和后台运行。
- Real Agent Runtime 的 run、steps、tool calls、traces、evidence 和 actions 已经绑定到工作空间。
- 写操作需要批准，符合企业 AI 的控制边界。

问题：

- 默认显示 7 个工具、模型/运行细节和 Tool Trace，技术过程比农业结果更抢占注意力。
- Demo 内容中固定出现 B-07 相似案例和多源数据，容易把演示结论误读为当前真实运行结果。
- Agent 完成后的结论与任务动作之间缺少清晰的“建议—风险—批准—已创建任务”状态链。
- “在后台继续”有入口，但后台运行记录、失败原因、重试和恢复路径没有成为明确工作流。

商业建议：以 Agricultural AI Analyst 为中心重排布局：左侧地块上下文，中间“正在回答的问题/当前进度/关键证据/结论”，右侧“待审批动作/任务状态”；工具轨迹仅作为可展开的审计信息。

### 4.5 Operations

**判断：已经有闭环接口，但还不像成熟的农事执行中心。**

优势：

- 页面能读取审批后的 Agent 任务，并显示字段、来源、证据数量、优先级和状态。
- 任务可回链 Agent 运行，证明 AI 推荐与 Operations 之间已经建立关系。
- 树体、水肥、病虫、清园等传统农事指导保留了农业场景价值。

问题：

- 任务列表缺少任务详情、责任人、计划时间、现场证据、执行结果、异常与关闭动作。
- 任务状态以文本 Tag 呈现，缺少统一状态机和跨页面可解释的状态定义。
- 页面内嵌外部专家 iframe，品牌、登录、隐私、加载失败和可访问性均不可控，削弱企业级可信度。
- Overview 的固定任务列表与 Operations API 列表之间缺少明确的实时/演示标识。

商业建议：将 Operations 重构为“待处理、执行中、已完成、异常”四列或队列，任务详情必须显示来源诊断、审批人、执行人、证据和关闭条件。

### 4.6 Knowledge & Expert

**判断：Human-in-the-loop 已存在，但 AI Learning Loop 仍未产品化。**

优势：

- 专家页面有待修改列表、案例详情、修改次数和复核状态。
- Agent 诊断复核、CONFIRMED/CORRECTED、历史候选等状态已经出现在界面。
- 后端具备专家复核和历史案例入库方向，为持续学习留下了数据结构。

问题：

- Knowledge Library 和 Cases 仍是占位页，用户看不到知识版本、来源、适用作物、质量和使用次数。
- 专家无法快速筛选高风险、低置信度、证据冲突或待入库案例。
- 专家修正后，哪些内容被采纳、何时进入检索、对模型/规则有什么影响不可见。
- 专家工作台仍偏“修正旧案例”，缺少批量审核、对比、备注、审计与绩效统计。

商业建议：把专家区分成 Review Queue、Case Library、Knowledge Sources、Learning Analytics 四个工作面，并为每条反馈提供采纳状态和可追溯版本。

### 4.7 Copilot

**判断：是一个有上下文意识的农业入口，但还不是完整的农业助手。**

优势：

- Drawer 能显示当前农场、地块、作物、物候、天气和当前页面上下文。
- 简单问题可以直接返回上下文提示，复杂问题可启动 Agent。
- 入口分布在 Header、Overview、Diagnosis，符合跨页面助手模式。

问题：

- 简单问题的回答是固定模板，没有证据、来源、时间和下一动作。
- 复杂问题以文本正则判断是否启动 Agent，用户无法理解为什么某个问题进入不同路径。
- 对话没有展示引用、风险等级、建议卡片、审批动作和历史会话恢复。
- Copilot 不具备明显的农业任务模板，例如“解释风险”“比较地块”“生成巡检任务”“追踪任务结果”。

商业建议：从聊天框升级为“农情 Copilot”：问题建议、证据引用、结论卡片、可审批动作和任务跟踪都在同一会话中完成。

## 5. AI Capability Presentation

| 能力 | 当前实现/展示 | 用户可感知程度 | 商业化判断 |
|---|---|---:|---|
| Multimodal RAG | Diagnosis 证据卡、Real RAG 标签、技术详情中的嵌入与 Milvus | 中 | 能证明能力存在，但默认视图没有把多源依据转为简洁决策解释 |
| Agent Runtime | Agent Workspace 的步骤、运行状态、实时绑定和后台运行 | 中高 | 产品表达最完整，但技术轨迹过多，需把结果和动作置于首位 |
| Tool Calling | 工具列表和工具状态 | 中 | 对开发者清楚，对管理者只应表现为“系统正在收集哪些依据” |
| Evidence Grounding | Evidence Tab、证据关系、来源与时间 | 高 | 是 FarMap 的可信度核心，应继续绑定每条建议和风险 |
| Human-in-the-loop | 专家复核、审批、CONFIRMED/CORRECTED、历史候选 | 中 | 流程已存在，但队列、责任、采纳和学习结果不透明 |
| Historical Case Learning | 历史案例 Retriever、Milvus 集合、专家确认候选 | 低中 | 技术基础已完成；当前真实案例为空时必须清楚表达“没有历史证据”，避免展示固定案例造成误导 |
| Model Routing | Technical View 显示主模型、升级模型、fallback | 低 | 适合 Expert Mode，不应成为业务用户的默认判断依据 |

展示原则：业务用户先看到“发现了什么、为什么、影响谁、建议做什么、需要谁批准”；专家再看到证据冲突、检索质量、模型路由、延迟与审计追踪。

## 6. Commercial Product Benchmark

不复制具体品牌 UI，只比较企业 AI 产品常见的产品原则：

| 企业产品原则 | FarMap 当前表现 | 差距 |
|---|---|---|
| 以业务对象和任务组织产品 | 已有 Farm、Field、Diagnosis、Task、Expert | 任务详情、责任人、结果回写尚未完整 |
| AI 结论必须可解释 | 证据卡、来源、时间、置信度已存在 | 证据与建议、冲突和复查条件不够直接 |
| 高风险写操作必须受控 | Agent action approval 已有 | 缺少统一审批中心和审计视图 |
| 用户随时知道系统状态 | REAL/DEMO、READY、等待审批等标签已有 | 页面级状态、失败、重试和数据新鲜度不统一 |
| AI 与人工共同工作 | Expert Review、Operations 已有 | 专家反馈采纳和学习结果不可见 |
| 从洞察到行动可闭环 | Diagnosis → Agent → Operations 可串联 | 执行结果和关闭证据缺失 |
| 多角色体验不同 | viewer/user/admin/expert 路由基础存在 | 不同角色的首页和任务优先级仍较接近 |

## 7. UX Problems

### P0 — 阻碍商业展示的问题

1. **REAL、DEMO、固定案例之间的边界不够强。** Overview、Diagnosis、Agent 同时使用高可信度的固定农情数字、B-07 历史案例、设备状态和时间。若演示模式标签被忽略，客户会误判数据真实性和 AI 运行结果。
2. **审批到任务执行没有一条可见的业务状态链。** 用户能看到“提交专家复核”和“批准创建任务”，但缺少统一的待审批、已批准、已创建、执行中、已完成、异常状态和责任人。
3. **核心商业页面仍有占位入口。** Knowledge Library、Cases、Operations Recommendations、Settings 中的模型/系统配置、部分详情动作仍是 Placeholder 或无完成反馈，影响客户对产品完整性的判断。
4. **关键动作存在“按钮可见但结果不确定”。** 生成报告、创建巡检任务、加入历史案例库、编辑地块等入口没有统一成功回执、错误回执和结果导航，演示过程中容易出现断点。

### P1 — 影响产品体验的问题

1. Overview 信息量大，但没有按风险影响、紧急度和责任人排序。
2. Digital Farm 的地图选择没有稳定地引导到 Field Intelligence、诊断或任务。
3. Diagnosis 默认视图暴露过多技术细节，业务结论、证据和建议的层级需要重排。
4. Agent Workspace 的 Tool Trace、工具名称和技术字段抢占了结论与待审批动作的空间。
5. Operations 缺少任务详情、执行证据、负责人、截止时间和异常处理。
6. Expert Review 缺少筛选、批量处理、冲突优先级和反馈采纳状态。
7. Copilot 的简单回答没有引用和可执行动作，复杂问题的路由规则对用户不可解释。
8. 外部专家 iframe 的加载、品牌和登录状态不可控，可能产生信任与隐私问题。
9. 空数据、接口失败、权限不足和真实数据延迟的状态表达不统一。
10. 中英文命名和“工作台/智能分析/Knowledge & Experts”等层级混用，增加跨角色培训成本。

### P2 — 优化增强问题

1. 建立统一的状态徽标、风险颜色、证据类别、审批状态和任务状态设计令牌。
2. 增加全局 Command/Search 的对象搜索结果，而不是仅按关键词跳转固定页面。
3. 增加诊断与任务的时间线、影响面积、历史趋势和地块对比。
4. 为 Copilot 增加农业任务模板、快捷问题和会话恢复。
5. 为多角色提供不同的首页视图：管理者看风险和任务，专家看复核队列，管理员看系统和模型状态。
6. 增加键盘焦点、地图替代文本、图表摘要、状态颜色之外的文本标识和移动/窄屏布局验证。
7. 将模型路由、Milvus、检索耗时和 Tool Trace 统一放入可折叠的 Expert Mode。

## 8. Design System Problems

当前样式已经建立 FarMap 的深绿色侧栏、浅色工作区、绿色主色、紫色 AI 色和风险状态色，但仍存在两套视觉语言并行的问题：旧页面使用 `--primary: #2e66e1` 等蓝色 token，新商业页面使用 `--fm-primary` 绿色 token；旧 `resp-*` 布局类与新 `fm-*` 产品类同时存在。

主要差距：

- 状态颜色在 Ant Design Tag、StatusBadge、自定义卡片和旧页面之间没有统一语义。
- 卡片、边距、标题层级和按钮尺寸在 Overview/Diagnosis/Agent 与旧页面不完全一致。
- 技术信息使用英文标签，业务信息使用中文标签，缺少统一的“业务名称 + 技术详情”层级规范。
- 图表、地图、监控预览和证据缩略图的空状态与加载状态没有统一组件。
- 移动端 CSS 已有断点，但复杂的 Diagnosis、Agent 和 Operations 三栏布局仍需要真实设备验证。

## 9. Demo Experience

10 分钟答辩/客户演示建议路径：

1. Overview：展示农场健康度、风险列表和“今日需要处理的事项”。
2. Digital Farm：选择 A-12，并展示空间风险与地块上下文。
3. AI Diagnosis：展示结论、三条关键证据和三条建议。
4. Copilot：提问“为什么 A-12 叶片黄化”，展示上下文和证据引用。
5. Agent Workspace：启动综合分析，只展示进度、证据和结论，不展开全部技术追踪。
6. Approval：批准一个低风险、可撤销的巡检任务。
7. Operations：打开任务详情，展示负责人、截止时间和执行证据。
8. Expert Review：展示确认/修正结果如何成为历史案例候选。

当前演示的主要卡顿点：

- Demo 路径与正式登录路径的切换需要解释。
- Agent 的步骤和工具较多，容易占用演示时间。
- Approval 与 Operations 的连接需要人工口头补充。
- Expert Review 依赖接口/外部 iframe 时，容易受环境和网络影响。
- 固定案例、固定时间和固定数量如果没有主动标注，会降低可信度。

## 10. Milestone 5.1 Commercial UI Redesign Roadmap

### Overview 改造方向

- 从“指标墙”改为“今日决策队列”：高影响风险、待审批建议、逾期任务、数据异常。
- 所有风险卡显示影响地块、影响面积、证据数量、置信度、责任人和下一动作。
- 增加全局 REAL/DEMO/数据更新时间提示，并让每个模块继承同一状态。
- 地图保留为入口，但选中地块后固定打开 Field Intelligence Panel。

### Diagnosis 改造方向

- 默认 Business Report：结论、风险、影响、依据、建议、审批动作。
- Evidence → Reasoning → Recommendation 采用纵向可追溯链，每条建议可展开依据。
- 技术详情、模型路由、向量库和延迟放入 Expert Mode。
- 所有操作提供成功、失败、待处理状态，并能回到任务或复核页面。

### Agent Workspace 改造方向

- 主标题改为“农业分析任务”，显示目标、地块、发起人和状态。
- 中央区域展示进度、关键证据、当前判断和下一步；工具调用折叠在审计抽屉。
- 右侧提供待审批动作卡，明确影响范围、风险、执行人、可撤销性和审批结果。
- 支持失败重试、暂停、后台运行、恢复和运行历史。

### Copilot 改造方向

- 从 Drawer 聊天改为上下文驱动的农情助手，提供问题模板和推荐问题。
- 回答必须包含来源、时间、证据、置信度和可执行动作。
- 支持“解释风险、比较地块、生成巡检任务、追踪任务、提交专家复核”等农业意图。
- 在会话内完成建议审批和任务状态回看。

### Operations 改造方向

- 增加任务中心：待审批、待执行、执行中、已完成、异常、已关闭。
- 任务详情显示来源诊断、Agent Run、审批记录、责任人、计划时间、现场证据和关闭条件。
- 用内部专家工作区替代不可控的外部 iframe，至少提供加载失败、权限和跳转状态。
- 记录“建议是否被采纳、实际执行结果、结果是否改善风险”，为后续学习提供业务反馈。

### Knowledge & Expert 改造方向

- 建立复核队列、案例库、知识源和学习分析四个明确入口。
- 支持按风险、置信度、证据冲突、作物和地域筛选。
- 展示专家修正前后、采纳状态、入库状态、版本和影响范围。

## 11. Priority Roadmap

### P0

1. 统一 REAL/DEMO/失败/待复核/已确认状态，并在 Overview、Diagnosis、Agent、Operations 同步显示。
2. 形成“建议 → 审批 → 任务 → 执行 → 关闭”的可见状态链与审计记录。
3. 为所有核心动作补齐成功、失败、等待和结果回链，消除按钮断点。
4. 把 Knowledge、Cases、Recommendations 与任务详情从占位/弱入口提升为可解释的最小可用商业页面。

### P1

1. 完成 Business View / Expert Mode 分层。
2. 为地图增加 Field Intelligence Panel。
3. 把 Operations 变成任务中心，补充负责人、截止时间、执行证据与异常。
4. 把 Expert Review 变成可筛选、可批量处理、可追踪采纳结果的队列。
5. 将 Copilot 的回答、证据和行动统一到一个农业任务会话。

### P2

1. 收敛旧 `resp-*` 与新 `fm-*` 设计语言，建立统一 token 与组件状态。
2. 增加多角色首页、趋势对比、移动端与无障碍验证。
3. 增加学习分析、风险关闭率、建议采纳率、专家一致性等商业指标。

## Final Assessment

FarMap V2 已经具备“农业 AI 决策平台”的可信产品叙事和技术基础，尤其在多模态证据、Agent 编排、审批边界和专家反馈方向上形成了差异化。当前距离完整商业 SaaS 的关键差距不在再增加模型或工具，而在把真实状态、责任、执行结果和学习反馈用稳定、低认知负担的 UI 连接起来。

Milestone 5.1 应优先完成商业 UI 分层与闭环状态表达，再扩展更多 AI 能力。完成 P0 后，FarMap 才适合以“可控、可解释、可执行”的农业 AI 产品对外进行正式商业演示。
